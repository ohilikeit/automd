# 1. Introduction

---

![image_1](https://raw.githubusercontent.com/ohilikeit/automd/master/data/outputs/images/SkillOpt/image_1.png)

**SkillOpt: Executive Strategy for Self-Evolving Agent Skills** (Microsoft, 2026)는 에이전트의 **스킬 문서(skill document)를 "학습 가능한 파라미터"로 취급**하고, 딥러닝 옵티마이저와 동일한 규율로 훈련시키는 방법을 제안합니다.

### 1. 배경 및 문제 제기

프론티어 모델은 이제 단일 프롬프트 호출자를 넘어 도구·파일·검증기를 갖춘 다단계 실행 하네스 안에서 동작합니다. 이런 환경에서 도메인 적응은 더 이상 모델 가중치나 프롬프트만의 문제가 아닙니다. **에이전트가 증거를 모으고, 도구를 부르고, 도메인 관례를 따르고, 출력을 포맷하는 "절차(procedure)" 자체를 개선해야 합니다.**

스킬(skill)은 바로 이 절차적 적응을 담는 자연어 아티팩트입니다. 문제는 지금까지 스킬이 만들어지는 방식입니다.

- **수작업 작성**: 전문가가 직접 쓰지만 타깃 도메인이나 하네스가 바뀌면 쉽게 깨집니다.
- **원샷 LLM 생성**: 태스크 설명만 보고 한 번에 뽑아내므로, 실제 롤아웃에서 관찰된 실패를 반영할 수 없습니다.
- **느슨한 자기 수정(self-revision)**: 에이전트가 스스로 스킬을 고쳐 쓰지만, **어떤 수정이 실제로 성능을 올렸는지 검증하는 절차가 없습니다.**

→ **셋 다 "옵티마이저처럼 동작하지 않습니다." 피드백을 받아도 시작점보다 확실히 나아진다는 보장이 없습니다.**

### 2. 제안: SkillOpt

논문의 핵심 아이디어는 한 문장으로 압축됩니다. **스킬 문서를 frozen 에이전트의 외부 상태(external state)로 보고, 가중치 최적화를 재현 가능하게 만든 바로 그 규율로 훈련시키자.**

구체적으로는 딥러닝 훈련 루프의 각 구성요소를 텍스트 공간에 1:1로 대응시킵니다. 위 Figure 1의 우측 상단 표가 이 대응 관계를 정리하고 있습니다.

| 딥러닝 | SkillOpt (텍스트 공간) |
| --- | --- |
| parameter (파라미터) | **skill document** — 훈련되는 대상 |
| gradient direction (그래디언트 방향) | **trajectory-derived edit direction** — 롤아웃에서 유도된 편집 방향 |
| learning rate (학습률) | **edit budget $L_t$** — 한 스텝에 허용되는 최대 편집 수 |
| validation check (검증) | **held-out selection gate** — 검증 점수가 오를 때만 편집을 수락 |
| stable training setting | batch / minibatch / schedule / gate |

Figure 1의 좌측 3D 손실 곡면이 이 논문의 직관을 잘 보여줍니다.

- **회색 점선(ad hoc updates)**: 기존의 무제한 자기 수정입니다. 한 번에 의미론적으로 크게 점프하기 때문에 곡면 위를 불안정하게 튕겨 다니다 **suboptimal skill**에 도달합니다.
- **파란 실선(bounded skill edits)**: SkillOpt입니다. 매 스텝 편집량을 제한하고(`bounded`), held-out 게이트(그림의 자물쇠 아이콘)를 통과한 편집만 수락합니다. 게이트를 통과하지 못한 **rejected side updates**(빨간 점선)는 버려지는 대신 **다음 스텝의 negative feedback으로 재활용**됩니다.
- 결과적으로 곡면을 안정적으로 미끄러져 내려가 더 나은 task-specific skill에 도달합니다.

> **왜 "bounded"가 결정적인가?**
> 연속된 스킬 리비전이 너무 멀리, 혹은 일관되지 않은 방향으로 움직이면 **거절된 편집과 이전에 수락된 편집이 더 이상 의미 있는 최적화 히스토리를 제공하지 못합니다.** 각 리비전이 직전 버전에 가깝게 머물러야만, 이후의 옵티마이저 호출이 "무엇이 도움이 되었고, 무엇이 실패했으며, 무엇을 보존해야 하는지"를 학습할 수 있습니다.

### 3. 핵심 결과

- 6개 벤치마크 × 7개 타깃 모델 × 3개 실행 하네스(direct chat, Codex, Claude Code)에서 평가한 **52개 (model, benchmark, harness) 셀 전부에서 최고 또는 동률 1위**를 기록했습니다.
- GPT–5.5 direct chat 기준 no-skill 대비 평균 **+23.5점**, Codex 루프 안에서 **+24.8점**, Claude Code 안에서 **+19.1점**.
- human-written / one-shot LLM / Trace2Skill / TextGrad / GEPA / EvoSkill 중 **셀마다 가장 강한 경쟁자만 골라 만든 오라클 베이스라인**보다도 평균 +5.4점 앞섭니다.
- 배포되는 산출물은 **300~2,000 토큰짜리 `best_skill.md` 파일 하나**입니다. 가중치 업데이트도, 추론 시점의 추가 모델 호출도 없습니다.

# 2. Method: 스킬을 "훈련"하는 루프

---

![image_2](https://raw.githubusercontent.com/ohilikeit/automd/master/data/outputs/images/SkillOpt/image_2.png)

Figure 2는 SkillOpt의 전체 파이프라인입니다. 왼쪽에서 오른쪽으로 데이터 흐름을 따라가 보겠습니다.

**1. 데이터 분할 (좌측 상단, DATASET)**
데이터셋을 세 갈래로 나눕니다. **Train split**은 롤아웃 증거를 생성하고, **Validation split**은 업데이트 게이트로만 쓰이며, **Test split**은 자물쇠 아이콘이 붙어 있듯 최종 보고 전까지 완전히 잠겨 있습니다. 즉 논문이 보고하는 모든 점수는 검증셋 과적합이 아니라 **일반화 성능**입니다.

**2. Forward Pass: 롤아웃 증거 수집 (Fixed Agent → Rollout batch)**
좌측 하단의 **Fixed Agent**에 자물쇠가, 스킬 문서 $S_t$에 불꽃 아이콘이 붙어 있는 것이 핵심입니다. **타깃 모델은 얼어 있고, 학습되는 것은 스킬 문서뿐입니다.** 현재 스킬을 주입한 상태로 훈련 배치를 실행해 궤적(trajectory), 도구 호출, 관측, 최종 답변, 검증기 피드백, 그리고 스코어를 수집합니다.

**3. Backward Pass: 미니배치 리플렉션 (mini-batch → Optimizer model)**
수집된 롤아웃을 성공/실패로 나누고 각각을 미니배치로 쪼갠 뒤, **별도의 프론티어 옵티마이저 모델**에게 넘깁니다. 미니배치 단위가 중요한 이유는 직관적입니다 — 단일 궤적은 일화적(anecdotal) 수정만 낳지만, **미니배치는 "에이전트가 계속 엉뚱한 출처를 검색한다", "답을 잘못된 포맷으로 쓴다", "도구 결과를 검증하지 않는다" 같은 재사용 가능한 절차적 오류를 드러냅니다.** 옵티마이저는 각 미니배치에서 구조화된 **add / delete / replace** 원자 편집을 제안합니다.

**4. Batch-level merge → Rank/clip by edit budget**
여러 미니배치가 낸 제안을 중복 제거하고 충돌을 해소한 뒤, 기대 효용 순으로 랭킹해 **상위 $L_t$개만 남깁니다.** 이 $L_t$가 텍스트 공간의 학습률이며, 기본값은 cosine decay를 적용한 $L_t = 4$입니다(하한 $L_t=2$). **이 클리핑이 ad hoc 프롬프트 재작성과의 결정적 차이입니다.** 무제한 재작성은 유용한 규칙을 지워버리거나, 서로 모순되는 지침을 넣거나, 하나의 국소 실패에 과적합될 수 있습니다.

**5. Validation gate (주황 마름모)**
후보 스킬 $S_{t+1}$을 **동일한 frozen 모델·하네스**로 검증셋에서 평가합니다. 현재 점수보다 **엄격하게 높을 때만** 수락합니다(동점은 거절). 이 게이트가 리플렉션을 "무조건적 자기 편집"이 아니라 **propose-and-test 최적화**로 바꿉니다. 그럴듯해 보이는 진단이 실제 타깃 모델의 성능을 해칠 수 있기 때문에 반드시 필요한 장치입니다.

**6. Rejected-edit buffer (분홍 박스, 빨간 점선)**
거절된 편집은 그냥 버려지지 않습니다. 어떤 편집을 시도했고 점수가 얼마나 떨어졌는지를 epoch-local 버퍼에 기록해, **같은 epoch의 이후 리플렉션 호출에 negative feedback으로 주입합니다.** 옵티마이저는 실패한 편집을 반복하지 않고 미해결 실패에 집중하게 됩니다. 중요한 점은 이것이 **훈련 시점에만 존재하고 추론 비용을 전혀 늘리지 않는다**는 것입니다.

**7. Epoch-wise slow/meta update (하단 청록 점선 영역)**
빠른 업데이트가 현재 배치에서 배운다면, 느린 업데이트는 **인접한 epoch 사이에서** 배웁니다. epoch가 끝나면 **동일한 훈련 샘플을 이전 epoch 스킬과 현재 epoch 스킬로 각각 실행**해(그림의 "same sample, different skills") 결과를 네 갈래로 분류합니다 — improvements(개선), regressions(퇴행), persistent failures(지속 실패), stable successes(안정 성공).

이 분류가 두 갈래로 흘러갑니다.

- **Slow update**: 옵티마이저가 장기적 가이던스 블록을 작성해 스킬 문서의 **보호된 slow-update 필드**에 씁니다. 스텝 단위 편집은 이 영역을 덮어쓸 수 없어서, 빠른 국소 수정과 느린 장기 통합이 분리됩니다. 이 후보 역시 검증 게이트를 통과해야 합니다.
- **Optimizer meta-skill** (보라 박스): "어떤 편집이 도움이 됐는지 / 실패했는지 / 어떤 실패가 남아 있는지"를 요약합니다. **이것은 옵티마이저 측에만 존재하며 배포 스킬에는 포함되지 않습니다.** 덕분에 배포되는 아티팩트는 컴팩트하게 유지되면서도 훈련은 풍부한 편집 히스토리의 이점을 누립니다.

→ **모멘텀 항이 epoch를 가로질러 안정적인 편집 방향을 실어 나르는 것과 같은 역할입니다.**

### 하네스 비종속성 (Harness-Agnostic Deployment)

SkillOpt는 경량 어댑터 인터페이스로 동작합니다. 어댑터는 훈련/평가 배치를 구성하고, 현재 스킬을 에이전트 컨텍스트에 주입하고, 네이티브 하네스를 실행해 채점된 궤적을 돌려줍니다.

- **Direct chat**: 스킬을 시스템 프롬프트에 prepend합니다.
- **Codex harness**: 워크스페이스 쓰기 가능 샌드박스에서 `codex` CLI를 구동하고, 스킬을 태스크별 `SKILL.md`로 렌더링합니다. 그리고 **`codex_trace_summary.txt`라는 압축 실행 트레이스를 다시 읽어 옵티마이저에게 넘깁니다.** 최종 답만이 아니라 **에이전트가 실제로 무엇을 했는지**로부터 학습한다는 뜻입니다.
- **Claude Code harness**: `claude` CLI를 통해 동일한 워크스페이스 계약을 따릅니다.

세 모드 모두 **같은 `best_skill.md` 포맷을 소비하며, 이것이 뒤에서 볼 cross-harness transfer 실험을 가능하게 합니다.**

# 3. Experiments: 52/52 셀 우위

---

**실험 설정**

- **벤치마크(6개)**: SearchQA(단일 라운드 QA), SpreadsheetBench(최대 30턴 멀티라운드 코드젠 + 실제 `openpyxl`/`pandas` 런타임), OfficeQA(최대 24회 도구 호출의 멀티턴 루프), DocVQA(멀티모달), LiveMathematicianBench(수학 MCQ), ALFWorld(에피소드당 최대 50스텝의 지속적 임베디드 상호작용). **의도적으로 이질적인 구성**입니다.
- **타깃 모델(7개)**: GPT–5.5 / 5.4 / 5.4-mini / 5.4-nano / 5.2, Qwen3.5–4B, Qwen3.6–35B-A3B. 프론티어급부터 소형까지.
- **베이스라인(7개)**: no skill, human skill(전문가 작성), one-shot LLM skill, Trace2Skill(궤적 증류), TextGrad(그래디언트 스타일 프롬프트 최적화), GEPA(Pareto 리플렉티브 프롬프트 진화), EvoSkill(실패 분석 기반 스킬 폴더 진화).

## 3.1 메인 결과

![image_3](https://raw.githubusercontent.com/ohilikeit/automd/master/data/outputs/images/SkillOpt/image_3.png)

Table 1이 이 논문의 핵심 결과 행렬입니다. 각 모델 블록 안에서 마지막 **SkillOpt 행(연보라 셀)** 이 나머지 6개 베이스라인과 경쟁하며, 작은 초록/빨강 아래첨자는 같은 블록 **No skill 행 대비 절대 변화량**입니다.

**관찰 1 — 모든 셀에서 승리.** 표를 세로로 훑어보면 SkillOpt 행의 볼드체가 사실상 모든 열에서 나타납니다. 7개 모델 × 6개 벤치마크(direct chat) + Codex/Claude Code 하네스의 GPT–5.5 5개씩, 총 **52개 셀 전부에서 최고 또는 동률**입니다. 프론티어급 GPT–5.5부터 4B짜리 Qwen3.5까지 균일하게 그렇습니다.

**관찰 2 — 가중치를 안 건드리는 방법치고 이득이 비정상적으로 큽니다.** GPT–5.5 direct chat 6개 벤치마크 평균이 58.8(no skill) → **82.3(SkillOpt)**, 즉 **+23.5점**입니다. 벤치마크별로 뜯어보면 편차가 의미심장합니다.

- SearchQA: 77.7 → 87.3 (**+9.6**) — no-skill이 이미 천장에 가까워 헤드룸이 작습니다.
- SpreadsheetBench: 41.8 → 80.7 (**+38.9**)
- OfficeQA: 33.1 → 72.1 (**+39.0**)
- LiveMath: 37.6 → 66.9 (**+29.3**)

→ **엄격한 절차와 답변 포맷 요구사항이 있는 벤치마크에서 이득이 압도적입니다. 이것이 정확히 zero-shot 프론티어 모델의 한계 지점이기 때문입니다.**

**관찰 3 — 작은 모델일수록 상대적 이득이 큽니다.** 6개 벤치마크 평균 향상폭은 GPT–5.4 +12.7, GPT–5.4-mini +15.4, **GPT–5.4-nano +26.7**, GPT–5.2 +16.6, Qwen3.5–4B +19.2, Qwen3.6–35B-A3B +9.1로, 모델당 평균 약 +17.6점입니다. GPT–5.4-nano는 DocVQA에서 30.8 → 80.2로 거의 2.6배, ALFWorld에서 34.3 → 69.4로 2배가 됩니다.

→ **컴팩트한 스킬 아티팩트가, 작은 모델이 아직 가중치 안에 갖고 있지 못한 절차적 지식을 공급해준다는 해석과 정확히 일치합니다.**

**관찰 4 — 도구 실행 환경에서도 동일하게 작동합니다.** 표 하단 Codex harness 블록에서 GPT–5.5는 5개 벤치마크 평균 no skill 대비 **+24.8점**, 차점자 EvoSkill 대비 +14.0점입니다. Claude Code harness에서는 no skill 대비 **+19.1점**, EvoSkill 대비 +3.2점입니다. 특히 Codex SpreadsheetBench는 27.5 → 85.0으로 **+57.5점**입니다.

**대안적 설명 배제.** 논문은 이득의 원인을 세 가지 후보로 나눠 반박합니다.
- *단순히 프롬프트가 길어서?* 아닙니다. human skill은 이미 145~516 토큰으로 one-shot LLM skill보다 길지만 모든 direct-chat 행에서 패배합니다.
- *옵티마이저 모델 용량 덕분?* 아닙니다. GPT–5.4-nano에서도 모든 베이스라인을 앞서고, 뒤에서 볼 optimizer strength 분석에서 타깃과 동일한 모델을 옵티마이저로 써도 이득의 56~74%가 회복됩니다.
- *특정 스킬 포맷을 악용?* 아닙니다. EvoSkill이 이미 Codex SpreadsheetBench를 27.5 → 67.5로 올렸는데, SkillOpt는 그 위에 **추가로 +17.5점**을 얹습니다.

## 3.2 Ablation: 무엇이 실제로 중요한가

논문의 하이퍼파라미터 스윕(Table 2, 생략)과 컴포넌트 절제(Table 3)를 대비해서 읽으면 이 방법의 성격이 선명하게 드러납니다.

**하이퍼파라미터에는 놀랍도록 둔감합니다.**
- 리플렉션 미니배치 크기를 1 → 32로 바꿔도 SearchQA는 85.9~87.1, SpreadsheetBench는 75.4~77.9 안에 머뭅니다.
- 롤아웃 배치 크기를 8 → 전체 epoch로 바꿔도 SearchQA 85.1~87.2, SpreadsheetBench 75.0~77.5입니다.
- 편집 예산 $L_t \in \{1,2,4,8,16\}$ 스윕에서도 작거나 중간 예산은 모두 경쟁력 있습니다.
- LR 스케줄러(constant/cosine/linear)도 87.3/80.7/62.1, 87.1/77.5/61.3, 87.2/72.9/62.9로 결론이 바뀌지 않습니다.

→ **헤드라인 이득이 "운 좋은 배치 크기 하나"의 산물이 아니라는 뜻입니다.** 다만 학습 증거의 양은 중요합니다 — 훈련 파티션을 1개 예제 → 100%로 늘리면 SpreadsheetBench가 47.5 → 78.0, LiveMath가 59.1 → 70.5로 올라갑니다(SearchQA는 20%만에 포화).

**반면 구조적 장치에는 매우 민감합니다.**

![image_4](https://raw.githubusercontent.com/ohilikeit/automd/master/data/outputs/images/SkillOpt/image_4.png)

Table 3은 세 가지 컴포넌트를 하나씩 제거한 결과입니다. 연보라 행이 기본 설정(SearchQA 87.1 / SpreadsheetBench 77.5 / LiveMath 61.3)입니다.

- **Learning-rate form**: `without lr`(편집 예산 없이 자유 재작성)로 가면 84.6 / 75.7 / 57.3으로 세 벤치마크 모두 떨어집니다. **어떤 형태든 적당한 유계 편집 예산이, 예산 없는 재작성보다 낫습니다.** `dynamic lr`(85.8 / 71.8 / 54.0)도 고정 예산보다 나쁩니다.
- **Rejected buffer**: 제거 시 85.5 / 72.9 / 58.9로 각각 −1.6, −4.6, −2.4점입니다. 거절된 편집을 negative feedback으로 재활용하는 것이 **기본 루프의 안정화 장치**로 실제 기여를 하고 있음을 보여줍니다.
- **Slow/meta update**: 여기가 가장 극적입니다. meta skill과 slow update를 **둘 다** 제거하면 SpreadsheetBench가 77.5 → **55.0 (−22.5점)** 으로 무너집니다. 전체 ablation에서 가장 큰 열화입니다.

> **왜 SpreadsheetBench가 유독 크게 무너질까?**
> 두 가지가 동시에 사라지기 때문입니다. (1) 장기 지평(long-horizon) 증거 스트림, (2) **국소 편집이 지속적 절차 지식을 덮어쓰지 못하게 막는 보호 영역 계약**. SpreadsheetBench는 최대 30턴의 멀티라운드 코드젠이라 여러 epoch에 걸쳐 축적된 워크북 수준의 절차가 성능을 좌우하는데, 보호 장치가 없으면 매 스텝의 국소 수정이 그 절차를 지워버립니다.

**검증 게이트가 실제로 일반화를 선택하는가?**

![image_6](https://raw.githubusercontent.com/ohilikeit/automd/master/data/outputs/images/SkillOpt/image_6.png)

Figure 3은 epoch 체크포인트별 성능 추이입니다. 가로축은 epoch 체크포인트(1, 2, 4, 8, 12, 16), 세로축은 hard score이며 세 개의 선이 그려져 있습니다 — **파란 실선(Train rollout)**은 훈련 롤아웃 점수, **주황 점선(Selection best)**은 검증셋에서의 선택 점수, **초록 일점쇄선(Unseen test)**은 한 번도 보지 않은 테스트셋 성능입니다.

- **(a) SpreadsheetBench**: 주황(선택)과 초록(테스트)이 epoch 1에서 각각 0.37, 0.50이었다가 epoch 2에서 0.80, 0.71로 함께 급등한 뒤 나란히 유지됩니다. **검증 게이트가 고른 체크포인트와 테스트 성능이 좋은 체크포인트가 일치합니다.**
- **(b) SearchQA**: 세 선이 0.82~0.87의 좁은 밴드 안에서 함께 움직입니다. 헤드룸이 작은 벤치마크의 전형적 모습입니다.
- **(c) LiveMath**: 주황(검증)이 0.765에서 오래 평평하다가 epoch 16에서 0.82로 뛰지만, 초록(테스트)은 0.57 근처에 머뭅니다. **검증-테스트 정렬이 항상 완벽하지는 않다는 것을 논문이 감추지 않고 보여주는 지점입니다.**

전반적으로 **검증 체크포인트가 held-out 테스트 성능을 추적하며, 게이트가 "선택 split에만 맞춘 스킬"이 아니라 일반화하는 스킬을 고르는 경향이 있음**을 확인시켜 줍니다.

**게이트의 엄격함과 감사 가능성.** 검증 게이트는 의도적으로 엄격합니다 — 후보 스킬은 선택 점수가 **strictly greater**일 때만 수락되므로 동점은 거절되고 배포 스킬이 조용히 드리프트하지 않습니다. 또한 매 스텝 편집별 accept/skip 상태를 담은 `edit_apply_report.json`을 기록해, **`best_skill.md`의 모든 변경 출처를 사후에 복원할 수 있습니다.**

## 3.3 Transfer: 최적화된 스킬은 재사용 가능한 아티팩트인가

![image_5](https://raw.githubusercontent.com/ohilikeit/automd/master/data/outputs/images/SkillOpt/image_5.png)

Table 4는 최적화된 스킬이 "태스크 전용 프롬프트"가 아니라 **이식 가능한 아티팩트**인지를 세 축으로 검증합니다. **Baseline**은 타깃의 no-skill 점수, **Direct**는 해당 환경에서 직접 최적화한 in-domain SkillOpt 점수, **Transferred**는 **추가 최적화 없이** 소스 스킬을 그대로 가져다 쓴 점수입니다.

**(a) Cross-model transfer — 모델 규모를 건너뛰기.**
GPT–5.4에서 훈련한 SpreadsheetBench 스킬을 GPT–5.4-mini에 그대로 얹으면 36.1 → 45.5(**+9.4**), nano에서는 23.5 → 26.5(+3.0)입니다. LiveMath에서는 mini +4.5, nano +5.6입니다. **네 행 모두 양의 전이이며, 그중 하나(LiveMath nano: 전이 28.8 vs in-domain 27.2)는 in-domain 최적화 결과를 오히려 넘어섭니다.** SpreadsheetBench mini는 in-domain 이득(+11.4)의 82%를 회수합니다.

→ **학습된 절차 중 일부는 타깃 모델에 무관(target-model agnostic)합니다.**

**(b) Cross-harness transfer — 실행 환경을 건너뛰기. 가장 강력한 배포 신호입니다.**
Codex 루프 안에서 훈련한 SpreadsheetBench 스킬을 Claude Code로 옮기면 22.1 → **81.8 (+59.7)** 으로, Claude Code에서 직접 최적화한 80.4를 살짝 넘어섭니다. 반대 방향(Claude Code → Codex)도 27.5 → 71.1(**+43.6**)입니다. LiveMath는 전이폭이 작지만(+1.6, +12.8) 여전히 양수입니다.

→ **두 하네스는 서로 다른 도구/파일 API와 커맨드 표면을 노출합니다. 그럼에도 전이가 되었다는 것은, 학습된 규칙이 하네스별 커맨드 레시피가 아니라 "구조 우선 검사, 수식 인지 검증, 정적 값 물질화" 같은 워크북 수준의 절차를 인코딩하고 있다는 뜻입니다.** 한 실행 환경에서 스킬을 최적화한 비용을 관련된 다른 배포 환경 전체에 분할 상환할 수 있습니다.

**(c) Cross-benchmark transfer — 가장 엄격한 이동.**
OlympiadBench에서 훈련한 스킬을 Omni-MATH에 적용하면 GPT–5.4 +3.7, mini +1.8, nano +1.3입니다. 이득폭은 앞의 둘보다 작은데, 당연합니다 — **테스트 인스턴스와 답변 포맷 관례가 **둘 다** 바뀐 뒤에도 유용한 절차 지식이 남아 있어야 하기 때문입니다.** 그래도 세 규모 모두 균일하게 양수라는 점이, 스킬이 벤치마크별 포맷을 암기한 게 아니라 재사용 가능한 수학적 절차를 담고 있다는 해석을 뒷받침합니다.

**옵티마이저 강도의 효과.** 별도 실험(Table 5)에서 강한 프론티어 옵티마이저(GPT–5.5)와 타깃과 동일한 모델을 쓴 옵티마이저를 비교합니다. 강한 옵티마이저가 모든 셀에서 더 큰 이득을 냅니다(GPT–5.4-nano SpreadsheetBench: +19.0 vs +11.9). 하지만 **타깃 매칭 옵티마이저도 강한 옵티마이저 이득의 56~74%를 회수**합니다.

> 이 대비가 중요한 이유는 **SkillOpt가 강한 교사에서 약한 학생으로의 distillation 파이프라인이 아님**을 보여주기 때문입니다. 최적화 루프 자체가 옵티마이저 능력 위에 실질적 가치를 더합니다. 게다가 옵티마이저는 **오프라인 훈련 중에만 호출되므로, 강한 옵티마이저를 쓰는 것은 배포 비용을 전혀 늘리지 않습니다.**

# 4. 학습된 스킬의 실체: 크기, 비용, 내용

---

메서드가 작동한다는 것과, 그 산출물이 실제로 쓸 만하다는 것은 다른 문제입니다. 논문은 학습된 아티팩트를 세 축으로 해부합니다.

![image_7](https://raw.githubusercontent.com/ohilikeit/automd/master/data/outputs/images/SkillOpt/image_7.png)

**컴팩트함.** 최종 `best_skill.md`는 379 토큰(LiveMath)에서 1,995 토큰(SpreadsheetBench) 사이, 중앙값 약 920 토큰입니다. 초기 스킬 대비 ×2.5~×53으로 자랐지만(초기가 한 줄짜리였는지 한 문단이었는지에 따라), **절대 크기는 여전히 현대 프론티어 모델의 시스템 프롬프트 예산에 한참 못 미칩니다. 도메인 실무자가 몇 분 안에 읽고 감사하고 직접 편집할 수 있습니다.**

**편집 경제성 — 이 표에서 가장 놀라운 열입니다.** `Edits` 열을 보면 6개 벤치마크 전체에서 실제로 `best_skill.md`에 반영된 편집이 **1~4회(중앙값 2.5회)** 에 불과합니다.

- LiveMath: **단 1회의 수락된 편집**으로 +29.3점
- OfficeQA: **단 1회의 수락된 편집**으로 +39.0점

→ **검증 게이트가 진짜로 일을 하고 있다는 직접적 증거입니다.** 옵티마이저 모델은 epoch당 훨씬 많은 편집을 제안하지만, held-out 검사를 통과해 배포 스킬까지 살아남는 것은 극소수입니다. 나머지 텍스트 공간 탐색은 rejected-edit 버퍼에 포착될 뿐 타깃 모델에는 도달하지 않습니다. **배포 스킬은 "모든 리플렉션의 합집합"이 아니라 그중 정제된 소수입니다.**

**포인트당 비용.** `Cost / pt` 열은 테스트 점수 1점을 올리는 데 든 훈련 토큰입니다. 두 가지 체제가 보입니다.
- **롤아웃이 짧고 저렴한 절차적 벤치마크**(SpreadsheetBench 0.6M, OfficeQA 1.1M, LiveMath 3.6M)는 포인트당 비용이 매우 낮습니다. **절대 이득이 가장 큰 벤치마크들이 동시에 가장 싸다는 점이 인상적입니다** — OfficeQA는 총 20.8M 토큰으로 +39.0점을 얻었습니다.
- **긴 궤적이나 풍부한 멀티모달 컨텍스트를 가진 벤치마크**(SearchQA 37.9M, DocVQA 46.4M)는 한 자릿수 배 더 비쌉니다.

배포 관점에서 결정적인 것은, **이 비용이 스킬 훈련 시점에 한 번만 지불된다**는 점입니다. export 이후 최적화된 `best_skill.md`는 옵티마이저 호출도, 가중치 업데이트도 없이 컴팩트한 텍스트 하나만 타깃 에이전트에 추가합니다.

## 학습된 규칙은 실제로 어떤 모습인가

![image_8](https://raw.githubusercontent.com/ohilikeit/automd/master/data/outputs/images/SkillOpt/image_8.png)

Figure 4는 벤치마크별로 최종 `best_skill.md`에서 **원문 그대로** 뽑아낸 대표 규칙 하나씩입니다. 세 가지가 눈에 띕니다.

**1. 인스턴스별이 아니라 절차적입니다.** 여섯 규칙 중 어느 것도 특정 질문, 파일, 엔티티를 지명하지 않습니다.
- *SpreadsheetBench*: "워크북 구조와 수식을 검사한 다음, Excel 재계산에 의존하는 대신 요청된 타깃 범위 전체에 걸쳐 **평가된 정적 값을 써라**."
- *ALFWorld*: "지평을 인식하는 방문/프론티어 원장을 유지하고, 같은 유형의 실패가 반복되면 탐색을 다변화하며, 타깃을 손에 넣기 전에는 목적지를 재방문하지 마라."

**2. 프론티어 모델이 zero-shot으로 갖추지 못한 "규율"을 일관되게 인코딩합니다.**
- **답변 포맷 제약** (OfficeQA: "추가 레이블 없이 요청된 반올림 값을 정확히 출력하라", LiveMath)
- **증거 결속** (DocVQA: "표·양식·차트·범례에서는 먼저 질문을 정확한 시각적 행/헤더/필드에 결속시킨 다음, 정렬된 답변 스팬만 복사하라")
- **워크북 구조 우선 추론** (SpreadsheetBench)
- **탐색 프론티어 관리** (ALFWorld)
- **정규 엔티티 선택** (SearchQA: "단서 표현에서 기대되는 답변 유형을 추론한 뒤, 함께 등장하는 변별적 증거로 뒷받침되는 **가장 짧은 정규 엔티티**를 골라라")

**3. 사려 깊은 인간 실무자가 하루 써보고 쓸 법한 규칙처럼 읽힙니다.** 차이는 이것이 **옵티마이저에 의해 자동 생성되고, held-out 데이터에서 편집 단위로 검증되었다**는 점입니다.

### 정성적 스킬 진화: 초기 스킬은 무엇에서 무엇으로 바뀌는가

논문은 두 개의 대표 실행을 추적합니다. 두 경우 모두 **SkillOpt는 초기 스킬을 무관한 프롬프트로 교체하지 않습니다. 수락된 편집들은 롤아웃에서 관찰된 반복적 실패 모드 주위에 컴팩트한 절차적 제약을 덧붙입니다.**

**ALFWorld** (학생 GPT–5.4-nano, 교사 GPT–5.5). 초기 스킬은 일반적인 가사 계획입니다 — 타깃 물체를 찾고, 집고, 필요하면 변형하고, 목적지에 놓아라. 수락된 편집들은 이 계획을 **더 상태 유지적(stateful)이고 루프에 덜 빠지게** 만듭니다.
- 정확한 물체명 매칭을 학습해 mug/cup, pan/pot 같은 유사 물체를 서로 대체하지 않습니다.
- 방문 위치 메모리를 추가해, 가능성은 높지만 이미 소진된 장소를 반복 확인하지 않습니다.
- 목적지 메모리, pick-two 진행 잠금, 직접 완료 규칙을 추가합니다 — 다음 서브골을 완료할 수 있게 되면 다시 살펴보거나 닫거나 검증하지 말고 **즉시 그 행동을 취하라.**

→ **일반적인 "탐색-변형-배치" 전략에서, 물체 정체성·탐색 메모리·진행 잠금·루프 차단기를 갖춘 유한 상태 실행 정책으로 진화합니다.** 이 실행에서 held-out 성능은 49.3 → 74.6이 되었습니다.

**SpreadsheetBench** (GPT–5.5가 학생이자 옵티마이저). 초기 스킬은 이미 "Python 스프레드시트 라이브러리를 쓰고 무관한 워크북 내용은 보존하라"고 지시합니다. 수락된 편집들은 이 일반적 자동화 워크플로를 **워크북 포렌식 정책**으로 바꿉니다.
- 프리뷰에 의존하지 말고 실제 워크북을 검사하고, 여러 시트에 걸쳐 헤더와 타깃 범위를 찾아내고, 조회/집계용 키와 셀 타입을 정규화하고, 구조 편집 중 서식을 보존하라.
- **핵심 규칙**: 채점기가 셀 값을 읽으므로, 프롬프트에 `INDEX/MATCH`나 `XLOOKUP` 같은 수식이 언급되더라도 에이전트는 **평가된 정적 값을 계산해서 써야 한다.**
- 이후 편집은 현재 비어 있는 결과 셀을 포함해 타깃 범위 전체를 채우고, 헬퍼 계산은 워크북 아티팩트를 늘리는 대신 Python 쪽에 유지하며, 저장된 워크북을 다시 열어 경계 행과 남은 공백을 확인하라고 요구합니다.

→ 이 실행에서 held-out 성능은 40.4 → 78.9가 되었습니다.

# 5. 정리

---

SkillOpt의 기여는 "스킬을 잘 만드는 또 하나의 방법"이 아니라, **스킬 개선을 ad hoc 프롬프트 수정에서 통제된 학습 과정으로 바꾼 것**입니다.

- **분리(separation)**: 태스크를 실행하는 타깃 모델과 스킬을 편집하는 옵티마이저 모델을 분리합니다. 옵티마이저는 오프라인 훈련에만 존재하므로 배포 비용이 0입니다.
- **통제(control)**: 유계 편집 예산(learning rate), 미니배치 리플렉션, held-out 검증 게이트, 거절 편집 버퍼, epoch 단위 slow/meta 업데이트 — 가중치 최적화를 재현 가능하게 만든 장치들을 텍스트 공간에 이식합니다.
- **결과**: 52/52 셀 최고 또는 동률, GPT–5.5 기준 direct chat +23.5 / Codex +24.8 / Claude Code +19.1점, 최강 per-cell 베이스라인 대비 +5.4점.
- **산출물**: 2,000 토큰 미만, 수락 편집 1~4회로 조립된 검사 가능한 텍스트 파일 하나. 모델 규모·하네스·인접 벤치마크를 가로질러 전이됩니다.

> **실무적 함의**: 스킬을 한 번 최적화하고, 텍스트로 감사하고, 모델 가중치를 바꾸지 않은 채 관련 모델·하네스·태스크에 재사용할 수 있습니다. Ablation이 그 이유를 설명합니다 — 유계 텍스트 학습이 무제한 재작성을 이기고, held-out 게이팅이 해로운 제안의 누적을 막고, 거절 버퍼가 실패한 편집을 negative feedback으로 바꾸고, slow/meta 업데이트가 배포 스킬을 부풀리지 않으면서 장기 지평 정제를 개선합니다.
